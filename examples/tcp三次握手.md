# TCP 三次握手：两次不行吗？

TCP 是传输层的快递员，负责把数据包可靠送达。三次握手，是它开工前的验货流程——就像打电话："喂？" "听见了，你能听见我吗？" "能。" 三步缺一不可。

## 完整流程

TCP 建连的过程涉及两个角色：客户端（发起方）和服务端（接收方）。初始状态：客户端 CLOSED（未连接），服务端 LISTEN（被动监听）。

> 每一步后面标注双方的**状态变化**——这是理解协议的关键。

### 第 1 步：Client → Server，发 SYN

客户端发一个 SYN 报文（SYN=1，随机序号 seq=x），意思是"我想连接你，这是我的起始序号"。

这一步验证了：**客户端能发出数据，服务端能收到**。但此时谁也不能确定反向通路是否畅通。

状态变化：**Client → SYN_SENT**（我发出了连接请求），**Server → SYN_RCVD**（我收到了连接请求，等你确认）。

### 第 2 步：Server → Client，回 SYN+ACK

服务端回应一个报文（SYN=1，ACK=1，自带序号 seq=y，确认号 ack=x+1）。意思是"收到你的 x，我接受连接；这是我的序号 y，你确认一下"。

`ack=x+1` 表示"我期待你的下一个序号是 x+1"——这同时验证了：**服务端能发出数据，客户端能收到**。

至此，两条"单行道"都验证通过：Client→Server 通了，Server→Client 也通了。

状态变化：**Client → ESTABLISHED**（两条路都通了，客户端单方面认为连接已建立），**Server 保持 SYN_RCVD**（已经发出回应，但还没收到客户端的最终确认）。

### 第 3 步：Client → Server，发 ACK

客户端回一个 ACK 报文（ACK=1，确认号 ack=y+1），意思是"我收到了你的 y，连接建立"。

服务端收到这个 ACK 后，双方进入 ESTABLISHED 状态，开始传数据。

状态变化：**Server → ESTABLISHED**（收到客户端确认，双向通道全部确认）。至此双方都是 ESTABLISHED，连接建立完成。

## 为什么不能只用两次

既然第 2 步就验证了双向通路，为什么非要第 3 次？两个理由：

**理由 1：服务端需要确认"客户端收到了我的序号"**

第 2 步之后，客户端知道了服务端的序号 y，但服务端不知道客户端是否收到了。如果只握手两次，服务端无法确认客户端的状态，等于"单向验货"。

**理由 2：防止失效的连接请求**

经典场景：客户端发了一个 SYN，网络拥堵导致延迟，客户端超时重发 SYN 并成功建连、通信、关闭。此时**第一个迟到的 SYN** 才到达服务器——如果只有两次握手，服务端会误以为又来了一个新连接，白白建立并一直等待资源。

第三次握手的作用就是：客户端收到迟到的 SYN 后，发现自己并没有发起新连接，于是不回应 ACK——服务端收不到 ACK，就知道这个请求已失效，不分配资源。

## 边界与例外

**半连接状态**：SYN Flood 攻击正是利用这一点——攻击者不断伪造 SYN，服务端进入 SYN_RCVD（半连接）等待 ACK，却不回复，导致服务端资源被耗尽。防御手段是 SYN Cookie：不分配资源，而是把一个带计算信息的 Cookie 放进 SYN+ACK 发回，等客户端 ACK 时再验证。

**面试常问**：既然三次握手这样建连，关闭连接为什么是"四次挥手"？——因为关闭是双向各自独立进行的：客户端关自己的发送方向，服务端关自己的，一来一回 ×2 就是四次。

## 记住它

**握手三次定双向监测**——牵手 SYN，回应 SYN+ACK，确认 ACK。两次验不完双向，三次刚好防住失效请求。
